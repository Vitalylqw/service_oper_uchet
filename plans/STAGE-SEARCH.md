# STAGE-SEARCH: Поиск по read-side в PostgreSQL

## Цель этапа

Добавить надежный и предсказуемый поиск по `read_deals` и `read_positions` в PostgreSQL
без лишней архитектурной сложности и без скрытого изменения sync flow.

Поиск должен покрывать реальные пользовательские сценарии:

- клиент;
- организация;
- поставщик;
- номенклатура;
- период;
- номер счета;
- дата счета;
- номенклатура поставщика;
- номенклатура клиента;
- клиент + номер счета;
- организация + номер счета.

## Что входит в scope

- проектирование поискового контура для PostgreSQL read-side;
- добавление индексов под структурный поиск;
- добавление полнотекстового поиска для текстовых полей;
- обновление репозиторного поиска без слома текущих сценариев;
- проверка влияния на полную синхронизацию;
- фиксация эксплуатационных действий после ночной пакетной записи;
- обновление проектной документации и журнала.

## Что НЕ входит в scope

- fuzzy search по опечаткам и `pg_trgm` на первом этапе;
- поиск по произвольным частям номера счета;
- изменение доменной бизнес-логики синхронизации;
- рефакторинг event store / read model builder вне задач поиска;
- изменение формата хранения `invoice_date`, если для этого потребуется отдельная миграция данных;
- API/UI и любые внешние точки входа поверх поиска;
- попытка сделать один универсальный индекс "на всё".

## Scope Validation

Текущая схема подходит для развития поиска:

- `read_deals` и `read_positions` уже являются денормализованным read-side;
- запись редкая, в основном ночная, крупными пакетами;
- PostgreSQL 16 и конфигурация `russian` уже доступны;
- основные поисковые поля уже существуют в read-модели.

Выявленные ограничения:

- текущий поиск в коде опирается на `ILIKE '%...%'`;
- в живой БД нет `GIN`-индексов и нет FTS-пути в схеме;
- основные дополнительные затраты лягут на `read_positions`;
- поле "Организация" пока трактуется как `seller`, если не будет подтвержден отдельный источник.

## Принятые решения

| Решение | Обоснование |
|---------|-------------|
| Поиск разделяется на структурный и полнотекстовый | Это надежнее и проще сопровождать, чем один общий механизм |
| `period`, `invoice_number`, `invoice_date` остаются структурными фильтрами | Для точных и составных запросов это предсказуемее FTS |
| FTS внедряется только для текстовых сущностей | Основной выигрыш нужен для клиента, организации, поставщика и номенклатуры |
| Первый релиз без `pg_trgm` | Уменьшаем сложность и стоимость записи |
| Первый релиз без триггеров | Меньше неявной логики и ниже риск побочных эффектов |
| Основной упор на `read_positions` | Реальные сценарии "номенклатура поставщика/клиента" живут именно там |
| После ночной синхронизации нужен `ANALYZE` по read-таблицам | Это безопасный минимум обслуживания после больших batch-операций |

## Целевые сценарии и источник данных

| Сценарий | Основная таблица | Механизм |
|----------|------------------|----------|
| По периоду | `read_deals`, `read_positions` | обычные индексы |
| По номеру счета | `read_deals` | обычный индекс |
| По дате счета | `read_deals` | обычный индекс |
| Клиент + номер счета | `read_deals` | составной индекс |
| Организация + номер счета | `read_deals` | составной индекс |
| Номенклатура поставщика | `read_positions` | FTS + составной индекс |
| Номенклатура клиента | `read_positions` | FTS + составной индекс |
| По клиенту / организации / поставщику / номенклатуре | `read_deals`, `read_positions` | FTS |

## Планируемая схема индексации

### `read_deals`

Сохраняются существующие индексы по периоду, статусам, дате создания и идентификаторам.

Добавляются:

- индекс по `invoice_number`;
- индекс по `invoice_date`;
- составной индекс `(client_name, invoice_number)`;
- составной индекс `(seller, invoice_number)` при условии, что `seller` = организация;
- полнотекстовый `GIN`-индекс по выражению, собранному из:
  - `client_name`;
  - `seller`;
  - `invoice_info`.

Причина выбора:

- отдельный индекс только по организации малополезен, так как уникальных значений 3-4;
- отдельный индекс по номеру счета нужен для точного поиска;
- клиент и организация хорошо работают как структурные фильтры в сочетании со счетом.

### `read_positions`

Сохраняются существующие индексы по `deal_id`, периоду, `hash_key` и ограничения целостности.

Добавляются:

- составной индекс `(supplier_name, product_name)`;
- составной индекс `(client_name, product_name)`;
- полнотекстовый `GIN`-индекс по выражению, собранному из:
  - `product_name`;
  - `supplier_name`;
  - `client_name`.

Причина выбора:

- именно `product_name` имеет очень большое число уникальных значений;
- `supplier_name` более селективен, чем организация и клиент;
- пользовательские сценарии чаще всего идут через связки "поставщик + номенклатура"
  и "клиент + номенклатура".

## Техническая стратегия реализации

### Шаг 1. Подготовка схемы

1. Подготовить Alembic-миграцию только для PostgreSQL-индексов поиска.
2. Добавить недостающие `btree`-индексы.
3. Добавить `GIN`-индексы на полнотекстовые выражения.

Примечание:

На первом этапе предпочтителен `GIN` по выражению `to_tsvector(...)`, а не отдельная
persisted-колонка `search_vector`. Это уменьшает связность ORM-моделей с PostgreSQL-спецификой
и снижает риск для SQLite fallback-сценариев.

### Шаг 2. Обновление кода поиска

1. Разделить фильтры и текстовый запрос.
2. Структурные условия строить отдельно:
   - период;
   - номер счета;
   - дата счета;
   - клиент;
   - организация.
3. Текстовую часть собирать через PostgreSQL FTS.
4. Комбинированные сценарии выполнять через `AND`.

### Шаг 3. Проверка производительности

Проверить:

- `EXPLAIN ANALYZE` на типовых сценариях;
- время полной синхронизации до/после;
- размер новых индексов;
- планы выполнения без непредсказуемых `Seq Scan` там, где ожидается индекс.

## Проверочные сценарии

Минимальный набор проверок:

1. Поиск по номеру счета.
2. Поиск по дате счета.
3. Поиск по периоду.
4. Поиск "клиент + номер счета".
5. Поиск "организация + номер счета".
6. Поиск "поставщик + номенклатура".
7. Поиск "клиент + номенклатура".
8. Поиск только по номенклатуре.

Для каждого сценария требуется:

- проверить результат на корректность;
- посмотреть план выполнения;
- зафиксировать, используется ли ожидаемый индекс.

## Оценка влияния на синхронизацию

Предварительная инженерная оценка:

- рост времени полной синхронизации вероятен;
- основной вклад дадут новые индексы на `read_positions`;
- безопасный минимальный набор индексов должен остаться приемлемым для ночной пакетной записи.

Ожидаемый порядок оценки:

- сначала замер "до";
- затем миграция и повторный замер "после";
- отдельно оценить размер и стоимость `GIN`-индекса на `read_positions`.

## Эксплуатация и обслуживание

После крупных ночных batch-операций:

- выполнить `ANALYZE read_deals`;
- выполнить `ANALYZE read_positions`.

Дополнительно:

- проверить, успевает ли `autovacuum`;
- отслеживать раздувание таблиц и индексов;
- не добавлять `VACUUM FULL` и регулярный `REINDEX` без подтвержденной необходимости.

## Риски и ограничения

1. Поле "Организация" может не полностью совпадать с `seller`.
2. `invoice_date` хранится строкой и может ограничить надежность поиска по дате.
3. Новые индексы увеличат стоимость ночной синхронизации.
4. Самым тяжелым по записи и размеру может стать `GIN`-индекс на `read_positions`.
5. Нельзя расширять первый релиз до fuzzy search и `pg_trgm`, пока не будет базового замера.

## Критерии успешности этапа

- основные пользовательские сценарии поиска покрыты;
- поиск работает через индексы, а не через полный перебор там, где это ожидается;
- sync flow не изменен логически;
- влияние на ночную синхронизацию измерено и зафиксировано;
- документация обновлена и отражает фактический способ поиска.
