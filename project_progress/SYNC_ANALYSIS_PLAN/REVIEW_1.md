## 2) Подтвержденные критические баги и быстрые фиксы

1) BUG‑001: audit не создается
- Файл: `src/infrastructure/workers/read_model_builder.py`, метод `_create_audit_entry` (около строки 1225).
- Причина: ранний `return` до создания записи.
- Рекомендация: удалить `return` и оставить лог + вставку `ReadModelAudit`. Быстрый фикс, минимальный риск.

2) BUG‑002: has_totals_error неправильно трактует NULL
- Файл: `src/infrastructure/workers/read_model_builder.py`, `_recalculate_totals` (1183–1189).
- Причина: `NULL` приводится к нулю, что создает ложные несоответствия.
- Рекомендация: если все `total_*` равны NULL → `has_totals_error = NULL`; иначе сравнивать только ненулевые `total_*` с `calc_*` по порогу 0.01. Логику выровнять с Domain.

3) BUG‑003 (вероятный): «Все как INSERT» при повторном запуске
- Возможная причина: при реконструкции из БД `deal_key` пересчитывается, а не берется из сохраненного значения (`repositories._read_model_to_domain` через `DealBuilder` с возможной нормализацией/фолбэками).
- Рекомендации (поэтапно):
  - A) Диагностика: залогировать пары `db_deal.deal_key` vs `excel_deal.deal_key` на этапе change detection.
  - B) Маппинг: при загрузке из БД сначала проставлять сохраненный `deal_key` как источник истины (или хранить и использовать `hash_deal_key`). Избегать фолбэков, меняющих смысл ключа.

## 3) Архитектурные пробелы, влияющие на надежность и масштабируемость

- Транзакции и идемпотентность:
  - Определить границы: запись batch событий — атомарно; обработка ReadModels — «per deal» или «per batch». Исключить commit внутри каждой item‑операции.
  - Гарантии «ровно один раз»: повторная обработка при сбоях, связь `event_id` ↔ `processed_at`, политика ретраев.

- Конкурентность:
  - Параллельные синхронизации/воркеры: порядок по `(aggregate_id, sequence_number)` и блокировки/ограничения.
  - Политика на «повторный запуск пока есть deferred».

- Унификация ключей:
  - Вынести генераторы `deal_key`/`hash_key` в единый модуль/сервис и переиспользовать в Domain/Detector/Builder, чтобы исключить расхождения (нормализация строк, scale, порядок полей).

- DeferredEventQueue:
  - In‑memory очередь теряет элементы при авариях. Для продакшена — таблица `deferred_events` с retry‑policy и TTL. In‑memory режим оставить как опцию для тестов.

- Коммит‑модель:
  - Перейти на commit per deal (или per batch), убрать commit из `_upsert_position()`; уменьшить накладные расходы и избежать частичных состояний.

- Индексы и наблюдаемость:
  - Обязательны индексы: `read_deals(deal_key UNIQUE)`, `read_positions(hash_key UNIQUE)`, `read_positions(deal_id)`, `event_store(aggregate_id, sequence_number)`, `event_store(processed_at)`.
  - Метрики: скорость/объемы на фазах, доля deferred, ретраи, latency до «processed_at».

- Числовая семантика:
  - Единый договор по точности Money/Money5 (5 знаков — где и почему), стратегии округления, формат сравнения.

- Partial sync:
  - Формализовать, какие периоды/листы затрагиваются, и как корректно вычислять deletions в частичном режиме.

## 4) Рекомендации с вариантами (плюсы/минусы)

- BUG‑001 (audit):
  - A) Удалить `return` (быстро). +Просто, −без батчинга.
  - B) Отдельный сервис аудита (batch insert). +Эффективно/масштабируемо, −сложнее внедрение.
  - Рекомендация: A сейчас, B — как улучшение.

- BUG‑002 (NULL totals):
  - A) Исправить сравнение в `_recalculate_totals` по логике Domain. +Быстро, −валидировать отображение NULL в UI.
  - B) Считать признак «несоответствия» исключительно на Domain‑уровне, а в БД хранить только итог. +Единый источник истины, −больше изменений.
  - Рекомендация: A сейчас; B обсудить.

- «Все как INSERT»:
  - A) Сохраненный `deal_key` как источник истины при чтении. +Устраняет расхождения, −требует осторожности.
  - B) Ввести/опереться на `hash_deal_key` (persisted). +Надежнее долгосрочно, −миграции/код.
  - Рекомендация: A → B (стратегически).

- Коммит‑модель:
  - A) per deal: +баланс надежность/перфоманс, −слегка сложнее, чем «внутри item».
  - B) per batch: +максимум эффективности, −сложнее откаты/диагностика.
  - Рекомендация: A.

- Deferred очередь:
  - A) In‑memory + «дожим» перед окончанием сессии. +Просто, −потери при авариях.
  - B) Persistent таблица. +Надежно, −доп.сложность.
  - Рекомендация: B для прод.

## 6) Метрики успеха (Acceptance)

- Повторный запуск на том же файле: 0 новых `DealCreated`/`DealItemAdded`.
- `has_totals_error`: при `total_* = NULL` — значение в БД не `true` (NULL/None допускается).
- `read_audit` наполняется (видны INSERT/UPDATE/DELETE), без деградации.
- Throughput не хуже текущего; «commit per deal» не ухудшает SLA.
- Доля deferred и ретраев контролируема; нет «зависших» событий без `processed_at`.
