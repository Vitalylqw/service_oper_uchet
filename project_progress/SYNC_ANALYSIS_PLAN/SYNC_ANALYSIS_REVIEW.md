### 1. Общая оценка плана (углубление)
План SYNC_ANALYSIS_PLAN.md — солидная основа для ревью. Он охватывает 7 блоков анализа, 3 подтвержденных бага, архитектурный обзор и рекомендации. Учитывая мою осторожность, я проверил: баги не были "задумкой" (e.g., return в _create_audit_entry — явная ошибка, не инвариант), но фиксы могут повлиять на производительность (больше записей в audit → рост БД). План сохраняет контекст CQRS: события только для изменений, read models для чтения.

**Углубленные плюсы:**
- Баги детализированы с примерами кода (e.g., BUG-002 с _delta и NULL → 0 — правильно идентифицировано как несоответствие domain логике в Deal.has_totals_error).
- Риски в блоках (e.g., R2.1 в Change Detector) учитывают edge cases, как пустая БД.
- Порядок выполнения логичен: сначала архитектура, чтобы не фиксить локально без понимания влияния.

**Углубленные минусы:**
- Нет анализа параллелизма: в read_model_builder process_latest_events может race condition при множественных sync (влияние на NFR-04 идемпотентность).
- Производительность: NFR цели (1000 строк/сек) не проверены; план не предлагает профилирование (e.g., с cProfile).
- Тесты: Отсутствуют конкретные примеры (добавлю ниже). Без них фиксы рискованны.
- Влияние на другие части: Не учтено, как фиксы повлияют на скрипты в scripts/services (e.g., run_sync_once.py — commit после orchestrator может не захватить audit).

**Замечания:** План осторожен, но недооценивает системное влияние. Например, фикс BUG-003 (deal_key в _read_model_to_domain) может изменить ID существующих сделок — проверьте на датасете, чтобы не сломать ссылки в event_store.

### 2. Углубленный анализ проекта
Проект следует лучшим практикам: DDD слои изолированы (domain без зависимостей, application координирует, infrastructure реализует). Ключ: синхронизация через SyncOrchestrator (парсинг → детекция → события → read models). Модели (Deal с uuid5 ID, hash_key из MD5) обеспечивают детерминизм. БД гибкая (SQLite/PostgreSQL). Но: в infrastructure/workers/read_model_builder.py много await в цикле — потенциал для батчинга.

**Углубленные сильные стороны:**
- Domain: DealBuilder обеспечивает инварианты (e.g., position_number уникален); calc_* computed fields точны с Decimal.
- Application: ChangeDetector использует hash для скорости, fallback на field_changes — эффективно.
- Infrastructure: EventStore с sequence_number гарантирует порядок; deferred_queue обрабатывает out-of-order события (хорошая задумка для robustness).

**Углубленные слабые стороны:**
- Производительность: В _recalculate_totals SELECT SUM по позициям — O(n) на каждое событие; на 1000+ items/deal замедлит (проверьте с EXPLAIN ANALYZE).
- Идемпотентность: Если deal_key меняется из-за нормализации (e.g., "UNKNOWN" fallback), повторный sync создаст дубли — подтверждаю гипотезу BUG-003.
- Логирование: Есть, но не везде (e.g., в simple_position_sync нет debug для deletions).
- Точность: Money5 OK, но в парсере float → Decimal может терять precision при формулах (xlcalculator hybrid — риск).

**Влияние изменений:** Фиксы не сломают задумку (e.g., no_cash с NULL сохранен), но добавьте индексы на deal_key в read_deals для ускорения find_by_period. Общее: + на надежность, но мониторьте БД размер (audit записи вырастут).
