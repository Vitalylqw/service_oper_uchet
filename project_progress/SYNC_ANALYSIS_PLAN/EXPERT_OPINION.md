## ЧТО МЕНЯ БЕСПОКОИТ

### 1. Отсутствие тестов - критическая проблема

При такой сложности архитектуры **отсутствие автоматизированного тестирования** - это бомба замедленного действия:

```python
# Нет тестов для:
- ChangeDetectorService (hash comparison, change detection logic)
- ReadModelBuilder (event processing, totals recalculation)
- Deal.has_totals_error (business logic)
- deal_key consistency (critical for change detection)
```

**Почему это критично:**
- Любое изменение может сломать change detection
- Регрессия в has_totals_error приведет к неправильным отчетам
- Без тестов на deal_key невозможно быть уверенным, что повторная синхронизация работает

**Моя оценка риска:** ВЫСОКИЙ

### 2. Дублирование бизнес-логики

```python
# Domain модель (правильная логика)
def has_totals_error(self) -> Optional[bool]:
    if all totals are None:
        return None
    # ...

# Infrastructure (неправильная логика)
def _delta(src: Decimal | None, calc: Decimal) -> Decimal:
    return abs((src or Decimal("0")) - calc)  # NULL → 0!
```

Это **классическое нарушение DRY**. Бизнес-логика определена в Domain, но продублирована (и неправильно!) в Infrastructure.

**Последствия:**
- Сложно поддерживать синхронность
- Ошибки при изменении одного места
- Нарушение Single Source of Truth

**Рекомендация:** Infrastructure должен **делегировать** расчет has_totals_error в Domain модель, а не дублировать логику.

### 3. Транзакционная целостность под вопросом

```python
# simple_position_sync.py
async def _upsert_position(...):
    # INSERT/UPDATE позиции
    await self.session.commit()  # ❌ Коммит в середине обработки

# Вызывается в цикле:
for item in deal.items:
    await self._upsert_position(item)  # Каждая итерация - отдельная транзакция
```

**Проблема:** Если падение происходит в середине цикла:
- Часть позиций записана
- Часть нет
- Inconsistent state
- Нет способа откатить всю операцию

**Это нарушает ACID принципы.**

## ЧТО ПРАВИЛЬНО, НО МОЖНО ЛУЧШЕ

### 1. Change Detection логика

Логика детекции изменений **архитектурно правильная**:
- Hash-based comparison для производительности
- Fallback на detailed comparison
- Использование deal_key как бизнес-ключа

**Но:**
```python
# detector.py:139
except Exception as e:
    logger.error(f"Failed to get database deals: {e}")
    return []  # ❌ Маскирует проблему
```

Возврат пустого списка при ошибке означает, что ВСЕ excel_deals будут помечены как INSERT. Это скроет реальную проблему (например, БД недоступна).

**Лучше:** Пробросить исключение наверх, пусть orchestrator решает, как обрабатывать.

### 2. Deferred Events механизм

Идея отложенных событий **правильная** (DealItemAdded может прийти раньше DealCreated).

**Но нет механизма:**
- Retry с экспоненциальным backoff
- TTL для устаревших событий
- Dead letter queue
- Мониторинга размера очереди

**Риск:** Очередь может бесконечно расти при системной проблеме.

### 3. Rollback on failure

```python
# orchestrator.py
if config.rollback_on_failure:
    logger.warning("Rollback on failure not yet implemented")
```

Это TODO на **критической функциональности**. Без rollback при падении в середине синхронизации система окажется в inconsistent state.

## СПЕЦИФИЧЕСКИЕ ТЕХНИЧЕСКИЕ ЗАМЕЧАНИЯ

### О BUG-001 (audit)

Это **тривиальная ошибка**, но с серьезными последствиями:

```python
async def _create_audit_entry(...):
    logger.debug(...)
    return  # ← Забыли убрать после отладки
    
    audit_entry = ReadModelAudit(...)  # Недостижимый код
```

**История ошибки (моя гипотеза):**
1. Разработчик временно отключил создание audit для отладки
2. Поставил `return` и logger.debug
3. Забыл убрать `return` после завершения отладки

**Исправление:** 5 минут (удалить 1 строку)  
**Риск:** Нулевой  
**Приоритет:** Немедленно

### О BUG-002 (has_totals_error)

Это **более серьезная проблема** - расхождение между Domain и Infrastructure логикой:

**Domain (правильно):**
```python
def _mismatch(src_money: Money | None, calc_amount: Decimal) -> bool:
    if src_money is None:
        return False  # NULL не ошибка
    return abs(src_money.amount - calc_amount) > THRESHOLD
```

**Infrastructure (неправильно):**
```python
def _delta(src: Decimal | None, calc: Decimal) -> Decimal:
    return abs((src or Decimal("0")) - calc)  # NULL → 0 ❌
```

**Почему это произошло (моя гипотеза):**
1. Разработчик сначала написал Infrastructure логику
2. Потом понял проблему с NULL
3. Исправил в Domain модели
4. Забыл исправить в Infrastructure

**Исправление:** 30 минут (привести к Domain логике)  
**Риск:** Низкий (становится идентично Domain)  
**Приоритет:** Критический

### О BUG-003 (deal_key mismatch)

Это **потенциальная проблема**, требующая проверки:

```python
# При загрузке из БД
builder.invoice_number = model.invoice_number or None
builder.seller = model.seller or "UNKNOWN"  # ← Fallback!

# При вычислении deal_key
num = (self.invoice_number or "").strip().lower()
seller = (self.seller or "").strip().lower()
```

**Анализ:**
- Если в БД `seller = NULL`, то при загрузке `seller = "UNKNOWN"`
- При вычислении deal_key: `"unknown"|...`
- Если в Excel `seller = ""`, то deal_key: `""|...`
- **MISMATCH!**

**Вероятность:** 30% (зависит от данных в Excel)  
**Влияние:** Критичное (все становится INSERT)  
**Проверка:** Unit-тест (1 час)  
**Приоритет:** Высокий
