## 2026-04-02 - Унификация runtime-загрузки `config.env` для CLI и DB-контура

### Цель:
Убрать расхождение между рабочим CLI-путём загрузки `config.env` и прямым созданием
`DatabaseConfig()` в infrastructure-слое, не меняя формат `config.env` и не ломая уже
работающие сценарии запуска.

### Контекст:
Диагностика после внедрения поискового этапа показала:

- CLI уже корректно загружал `config.env`;
- `DatabaseConfig` ожидал переменные вида `DB_DB_*` из-за `env_prefix="DB_"` и имен полей
  `db_host`, `db_name`, `db_user` и т.д.;
- фактический `config.env` содержит рабочие переменные в legacy-виде:
  `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`;
- из-за обхода CLI-loader'а async PostgreSQL runtime читал дефолтные значения и
  не подключался к целевой БД.

### Принятые решения:
- не менять формат `config.env`;
- не вносить локальный костыль только в `connection.py`;
- вынести общий loader в нейтральный infrastructure-модуль;
- переиспользовать тот же механизм и в CLI, и в DB runtime;
- сохранить backward compatibility через promotion legacy DB-переменных в `DB_DB_*`.

### Выполненные действия:
1. Создан общий модуль `src/infrastructure/config/env_loader.py`.
2. В него перенесены:
   - загрузка `config.env` через `dotenv`;
   - promotion `DB_HOST -> DB_DB_HOST` и остальных legacy DB-переменных.
3. `src/cli/common.py` переведён на новый общий loader без изменения публичного поведения.
4. `src/infrastructure/database/connection.py` обновлён так, чтобы общий loader вызывался до
   первого создания `DatabaseConfig()`.
5. `src/infrastructure/database/repositories.py` дополнительно скорректирован для async PostgreSQL:
   веса `setweight(...)` передаются как SQL `char` literal, а не как bind-параметры.
6. Выполнена поэтапная проверка:
   - `py_compile` для изменённых модулей;
   - `so-uchet --env-file ./config.env db test`;
   - raw `asyncpg` подключение без ручного проброса `DB_DB_*`;
   - end-to-end вызов `search_deals()` через реальный async PostgreSQL runtime.

### Результат:
- `config.env` теперь одинаково работает и для CLI, и для DB runtime;
- формат конфигурационного файла не менялся;
- проблема с чтением PostgreSQL-параметров устранена без дублирования логики в разных слоях;
- поисковый runtime-путь подтверждён не только через `EXPLAIN`, но и через реальный async-вызов.

### Зачем:
Чтобы убрать скрытое расхождение между слоями запуска, снизить риск ложных дефолтов в DB-конфиге
и зафиксировать единый проектный путь загрузки runtime-переменных из `config.env`.

## 2026-04-02 - Проектирование поискового этапа для PostgreSQL read-side

### Цель:
Подготовить надежный и минималистичный этап внедрения поиска по `read_deals` и
`read_positions` без скрытого усложнения sync flow и с обязательной оценкой влияния на ночную
пакетную синхронизацию.

### Контекст:
Проверка живой PostgreSQL БД показала:

- `read_deals` содержит около 50 тыс. строк;
- `read_positions` содержит около 294 тыс. строк;
- конфигурация `russian` уже доступна в PostgreSQL;
- в active schema отсутствуют `GIN`-индексы и явная поддержка FTS;
- текущий поиск в репозитории использует `ILIKE '%...%'`.

Пользовательские сценарии поиска сосредоточены вокруг:

- клиента;
- организации;
- поставщика;
- номенклатуры;
- периода;
- номера и даты счета;
- комбинаций "поставщик + номенклатура", "клиент + номенклатура",
  "клиент + номер счета", "организация + номер счета".

### Принятые решения:
- разделить поиск на структурный и полнотекстовый;
- не пытаться решать период, номер и дату счета через FTS;
- основной акцент сделать на `read_positions`, где живут сценарии по номенклатуре;
- не включать `pg_trgm` и fuzzy search в первый релиз;
- включить в этап обязательный замер влияния новых индексов на ночную синхронизацию;
- зафиксировать post-sync обслуживание через `ANALYZE`.

### Выполненные действия:
1. Проведена сверка схемы, индексов и текущего кода поиска.
2. Проверено фактическое состояние живой БД:
   - PostgreSQL 16;
   - доступность `russian` text search config;
   - отсутствие `GIN`-индексов по `read_deals` / `read_positions`;
   - текущие размеры и объемы read-таблиц.
3. Подготовлен детальный stage-план: `plans/STAGE-SEARCH.md`.
4. Обновлены active project docs:
   - `PROJECT_PLAN.md`;
   - `STATUS.md`;
   - `PROJECT_OVERVIEW.md`;
   - `DEVELOPMENT_JOURNAL.md`.

### Результат:
- зафиксирован отдельный этап по поиску с четким scope;
- определен минимальный набор индексов и FTS-подход без лишней сложности;
- этап готов к реализации через миграции, обновление репозитория и последующие замеры.

### Зачем:
Чтобы перейти от текущего `ILIKE`-поиска к надежному read-side поиску, не ломая sync-контур
и не вводя сложность, не подтвержденную реальными сценариями использования.

## 2026-03-14 - Проектирование CLI-обёртки `so-uchet`

### Цель:
Создать единую CLI-точку входа для всех операций приложения: синхронизация,
снапшоты, дашборды, управление БД.

### Контекст:
Приложение не имеет собственного runtime — его вызывают внешние приложения или
оператор напрямую через Python-скрипты. Отсутствует стандартизированный способ
взаимодействия. CLI решает эту задачу.

### Принятые решения:
- фреймворк: `click` — зрелый, стабильный, минимум магии;
- имя CLI: `so-uchet` (совпадает с именем пакета);
- расположение: `src/cli/` — отдельный presentation layer;
- старые скрипты остаются на месте, CLI — дополнение, а не замена;
- реализация разбита на 5 подэтапов.

### Выполненные действия:
1. Проведён анализ всех точек входа и функциональных блоков приложения.
2. Определён полный набор CLI-команд: `sync` (5), `snapshot` (2), `dashboard` (3), `db` (3).
3. Создан детальный план: `plans/STAGE-CLI.md`.
4. Обновлена проектная документация:
   - `PROJECT_PLAN.md` — добавлен Этап B;
   - `STATUS.md` — CLI в разработке, приоритет, текущие задачи;
   - `PROJECT_OVERVIEW.md` — CLI в scope, архитектуре и навигации;
   - `DEVELOPMENT_JOURNAL.md` — текущая запись.

### Результат:
- зафиксирован план из 5 подэтапов с чёткими границами scope;
- документация актуализирована под новый этап;
- готовность к началу реализации (подэтап 1: каркас + команда `db`).

### Зачем:
Стандартизировать взаимодействие с системой, дать операторам и внешним приложениям
единую точку входа вместо набора разрозненных скриптов.
