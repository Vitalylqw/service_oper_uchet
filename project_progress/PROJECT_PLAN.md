# План проекта

## Цель

Поддерживать надежный и проверяемый контур синхронизации:

- Excel -> parsing;
- parsing -> change detection;
- change detection -> event_store;
- event_store -> read models;
- read models -> snapshot/dashboard-проверки.

## Активный scope

1. Удерживать в актуальном состоянии Excel-based sync flow без возврата скрытой сложности
   `is_active/version`.
2. Сохранять согласованность между кодом, миграциями, тестами и документацией.
3. Поддерживать технические инструменты проверки:
   `scripts/test/`, `dashboard/`, `read_stats`, `db_snapshots`.
4. Предоставить единую CLI-точку входа для всех операций системы.
5. Подготовить надежный поисковый контур по read-side в PostgreSQL под реальные
   пользовательские запросы.

## Текущий этап

### Этап A. Актуализация документации

Что входит:

- привести активную документацию к текущему scope проекта;
- убрать противоречия с кодом и реальной структурой репозитория;
- перенести исторические техотчеты в архив без потери информации;
- зафиксировать канонические документы для входа в проект.

Что не входит:

- изменение бизнес-логики синхронизации;
- рефакторинг кода без отдельной задачи;
- переработка конфигурационной модели `.env` / `config.env`.

### Этап B. CLI-обёртка `so-uchet`

Детальный план: `plans/STAGE-CLI.md`.

Цель: создать единую CLI-точку входа для всех операций приложения.
Приложение не имеет собственного runtime — его вызывают внешние приложения
или оператор. CLI становится стандартным способом взаимодействия.

Подэтапы:

1. Каркас CLI + команда `db` — entry point, общая инфраструктура.
2. Команды `sync` — full/partial/periods/status/list.
3. Команды `snapshot` — create/list.
4. Команды `dashboard` — latest/compare/excel-health.
5. Финализация — стабилизация, проверка, документация, commit.

Что входит:

- модуль `src/cli/` как presentation layer;
- entry point `so-uchet` в `pyproject.toml`;
- обновление проектной документации.

Что не входит:

- изменение бизнес-логики синхронизации;
- рефакторинг domain/application/infrastructure слоёв;
- удаление или перемещение существующих скриптов;
- изменение схемы БД или миграций.

### Этап C. Поиск по read-side в PostgreSQL

Детальный план: `plans/STAGE-SEARCH.md`.

Цель: внедрить надежный и предсказуемый поиск по `read_deals` и `read_positions`
без лишней сложности, с отдельной оценкой влияния на ночную пакетную синхронизацию.

Подэтапы:

1. Документирование и фиксация поискового контракта.
2. Миграции и индексы для PostgreSQL.
3. Обновление репозиторного поиска.
4. Проверка производительности и эксплуатационные действия.

Что входит:

- индексы для периода, счета и составных поисковых сценариев;
- полнотекстовый поиск по клиенту, организации, поставщику и номенклатуре;
- измерение влияния на sync;
- фиксация обслуживания read-side после ночных batch-операций.

Что не входит:

- fuzzy search и `pg_trgm` в первом релизе;
- изменение бизнес-логики sync flow;
- переработка API/UI;
- миграция формата `invoice_date`, если для этого потребуется отдельный шаг.

- зафиксировать post-sync обслуживание через `ANALYZE` и контроль bloat.

### Направление 3. Конфигурация окружения

- зафиксировать каноническую схему env-конфигурации;
- при отдельном согласовании свести использование `config.env` и `.env` к понятному правилу.

## Ограничения и риски

- Исторические документы нельзя удалять без проверки их ценности для архитектурной памяти.
- Документация не должна утверждать то, что не подтверждено кодом или фактической проверкой.
- Любые будущие изменения sync flow нужно сначала сверять с `project_goals.md`.
- Поисковый контур должен проектироваться под реальные сценарии, а не под абстрактный
  "универсальный поиск".
